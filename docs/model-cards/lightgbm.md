## Intended use

Scores individual SEPA Instant Credit Transfers for financial-crime risk, inside the ten-second settlement window, to raise an alert for human review.

**In scope.** Ranking transactions for a compliance analyst's queue; supplying the explanation that accompanies an alert.

**Out of scope, explicitly.** Creditworthiness assessment, automated account closure, and any decision taken without human review. This is a *triage* model: it decides what a person looks at, not what happens to a customer.

## Regulatory position

AML transaction monitoring is **not** an Annex III high-risk system under the EU AI Act. It is governed by the AML package (AMLR/AMLD) and BaFin's interpretive guidance, with DORA and MaRisk applying to its operational resilience and model risk management.

Creditworthiness assessment *is* Annex III high-risk — and this model does not perform it. Stating that distinction precisely is the point; a card claiming blanket "AI Act compliance" for an AML model would be describing the wrong instrument.

Because scores contribute to automated decisions affecting individuals, **DSGVO/GDPR Art. 22** applies. See `docs/ai-act-memo.md` for the full analysis and `kg serve verify-log` for the decision log that supports it.

## What the labels can and cannot show

The label stream captured **14.5%** of the crime actually present — 434 of 2,995 transactions.

Every precision figure above is therefore an **upper bound**: transactions that are genuinely criminal but were never confirmed sit in the negative class and count against precision when the model finds them.

| Scored against | PR-AUC |
|---|---|
| the label stream | 0.0036 |
| ground truth | 0.0186 |

The second row is only computable because the data is simulated. A real institution could not produce it — which is precisely why the simulator exists (design principle P9).

Splits are **chronological**, never random. A label enters a fold only if its `decided_ts` precedes that fold's boundary — a label whose transaction is in the training window but whose decision came later does not exist as far as training is concerned.

**The data is synthetic.** It is generated by an agent-based simulator of a German retail payments ecosystem, calibrated against public aggregates. It is described as a simulator throughout and is not presented as real customer data.

## Serving artifact

A model card should say which artifact actually makes the decisions, because a format conversion is a model change until measured otherwise.

**The gateway serves the LightGBM booster in-process.** An ONNX graph is exported alongside it for portability, and it is *not* the serving path: scored against 303,129 held-out feature vectors it changes 774 decisions (0.2553%) and raises 7,232 alerts where this model raises 6,458 — an alert-set Jaccard of 0.8930.

The cause is precision: ONNX scores tree ensembles in float32, LightGBM accumulates in float64, and the operating threshold of 3.98e-04 is small enough that the rounding crosses it. See [ADR-0008](../adr/0008-onnx-runtime-not-triton.md).

## Known limitations

- **Trained on simulated data.** Behaviour on real payment traffic is unknown. The simulator's calibration targets are public aggregates, not licensed microdata.
- **Labels are incomplete and selection-biased.** Confirmation requires the incumbent rules engine to have flagged the case first, so the label stream systematically under-represents evasive typologies.
- **Precision figures are upper bounds** for the reason stated above.
- **No fairness assessment has been performed.** The simulator generates names reflecting Germany's largest immigrant communities, which means a disparate-impact analysis across name origin is *possible* and has not been done. That is a gap, not an absence of risk.
- **Concept drift is unmeasured over long horizons.** The evaluation covers a single simulated period.
